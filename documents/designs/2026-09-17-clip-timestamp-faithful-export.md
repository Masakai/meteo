## 1. 問題

検出クリップ（MP4）が実際の映像より速く再生される。
v3.17.2、v3.18.0、v3.17.4で3回修正したが再発している。

2026-09-17時点でgreeng4に残っていた検出クリップ5件について、全フレームのOSD時刻をOCRで読み、書き出しfpsと比較した。

| ファイル | 稼働バージョン | 書き出しfps | OSD実測fps | 判定 |
|---|---|---|---|---|
| camera2 `meteor_20260819_005802_a8a610fc` | v3.19.x（クランプなし） | 19.75 | 約10（秒あたり3〜7フレームの欠落区間あり） | 約2倍速 |
| camera2 `meteor_20260819_034211_bb44002e` | v3.19.x（クランプなし） | 19.75 | 10 | 約2倍速 |
| camera3 `meteor_20260819_040423_4cc6630a` | v3.19.x（クランプなし） | 10.58 | 10 | 正常 |
| camera3 `meteor_20260823_024013_d80ad9c5` | v3.17.3-rollback | 11.0 | 10 | 正常 |
| camera1 `meteor_20260917_030951_62626009` | v3.17.4（クランプあり） | 20 | 10 | 2倍速 |

過去の記録（`memory/log_server-changes.md` 2026-08-24、2026-08-25）には、実測7〜13fpsに対して210fps・226fps、実測2.2fpsに対して174fpsで書き出された事例もある。

## 2. 原因

### 2.1 確認できた事実

- Tapo C120は夜間、実効10fpsで映像を送る。RTSPのネゴシエーション値は昼夜とも20.0fpsのままである（greeng4のログ `接続成功: 2560x1440 @ 20.0fps`、およびOSD実測）。
- 同じ夜間10fpsの条件で、書き出しfpsが正しい時（10.58、11.0）と2倍になる時（19.75、20）がある。
- 9/17の事例では、クリップの受信時刻上の長さ（検出0.629秒+前後マージン3.0秒×2=約6.6秒）と、OSD上の長さ（6.3秒）はほぼ一致していた。受信時刻はクリップ全体で見れば実時間と対応している。
- 9/17 03:09前後のホストCPUはidle約60%（sar）。夜間00〜07時の平均使用率は49%。CPUは飽和していない。

### 2.2 過去の原因説明の訂正

CHANGELOG（v3.17.3、v3.17.4）と `estimate_fps_from_frames()` のdocstringは、原因を「CPU飽和で `cap.read()` の間隔が乱れるため」としている。
2.1のとおり、9/17の事例はCPUに余力がある状態で発生しており、この説明は少なくとも今回の事例には当てはまらない。
「各カメラコンテナ99%前後」という過去の記述は、`docker stats` の1コア基準の値（4コア機では400%が上限）を指していた可能性があるが、当時の測定値は今回確認していない。

### 2.3 設計上の欠陥

`RingBuffer` は全フレームを `(受信時刻, 画像)` で保持している。
しかし `save_meteor_event()` は書き出し時に、この時刻列を `estimate_fps_from_frames()` で1個のfps値に潰し、ffmpegへ `-r <fps>` と `-fps_mode cfr` で渡している。
フレームごとの時刻はここで捨てられ、全フレームが等間隔として書き出される。

この構造には2つの欠陥がある。

1. **1クリップを1個のfps値で表す前提が成り立たない。**
   フレーム欠落（8/19 `005802` の秒あたり3〜7フレームの区間）や、昼夜切替時のfps変化があると、どの値を選んでもクリップのどこかで再生速度がずれる。
2. **その1個の値を、フレーム間隔の中央値で推定している。**
   フレームが等間隔で届かない場合、中央値は平均的な間隔を表さない。
   例えば間隔が0.05秒、0.05秒、0.2秒の繰り返しなら、平均は10fpsだが中央値は0.05秒で20fpsになる。
   ほぼ同時に届くフレームが半数を超えれば200fps前後になる。
   19.75fps（=1/0.0506秒）、210fps、226fpsという観測値はこの形で説明できる。ただし夜間の受信間隔の分布は未計測で、この説明は仮説である（7章）。

過去3回の修正は、いずれもこの推定値の後処理だった。

| リリース | 内容 | 効かなかった理由 |
|---|---|---|
| v3.17.2 | 30fps固定への上書きバグを削除 | 推定値がそのまま使われるようになり、推定の誤りが表に出た |
| `sanitize_fps()` | 1〜120fpsの範囲外を棄却 | 19.75や108は範囲内 |
| v3.18.0 / v3.17.4 | ネゴシエーション値の1.5倍超を棄却して20fpsに置換 | 夜間の真値は10fpsで、置換先の20fps自体が誤り |

## 3. 対策方針

fps推定をやめる。
クリップは一定fps（CFR）のまま、各フレームを自分の時刻の位置に置いて書き出す。

- 出力fps（`out_fps`）はRTSPのネゴシエーション値（`reader.fps`、`sanitize_fps()` 適用後）に固定する。
- 出力のk番目のフレームの時刻を `t0 + k / out_fps` とし、その時刻以前で最新の入力フレームを割り当てる。
- 実効10fpsの区間では同じフレームが2回ずつ入る。欠落区間では直前のフレームが続く。途中でfpsが変わっても、その区間の複製回数が変わるだけである。
- 再生時間は常に `最後の時刻 − 最初の時刻` と一致する（誤差は `1/out_fps` 秒以内）。

この方式では、再生速度を決める値が推定値ではなくなる。
中央値か平均か、クランプの閾値をいくつにするか、という調整項目そのものが消える。

CFRを維持する理由は、現行のFacebook互換要件（`force-cfr=1`、`-fps_mode cfr`、`15360 tbn`）を変えないためである。

### 3.1 検討した代替案

| 案 | 内容 | 不採用の理由 |
|---|---|---|
| A. 推定式を全体平均に変更 | `(n−1) / (t_last − t_first)` | 今回の5件はすべて約10fpsになり改善する。ただし1クリップ1値の前提は残り、欠落やfps変化のあるクリップで速度がずれる。推定に依存する構造も残る |
| B. 真のVFR出力 | フレームごとにPTSを付けて書き出す | rawvideoのパイプ入力ではフレーム単位のPTSを渡せず、コンテナ形式の変更か中間ファイルが必要。Facebook互換のCFR要件とも両立しない |
| C. クランプ閾値の再調整 | 夜間10fpsを基準にする等 | 推定値の後処理であり、過去3回と同じ種類の修正 |

### 4.2 新規関数 `resample_frames_to_cfr()`

```python
class ResampleStats(NamedTuple):
    n_out: int       # 出力フレーム数
    n_used: int      # 出力に現れた入力フレーム数
    n_dropped: int   # 出力に現れなかった入力フレーム数
    max_run: int     # 同一フレームの最大連続回数


def resample_frames_to_cfr(
    frames: List[Tuple[float, np.ndarray]],
    out_fps: float,
    stats: Optional[List[ResampleStats]] = None,
) -> Iterator[np.ndarray]:
    """フレームを時刻どおりに一定fpsの格子へ再配置する"""
```

- 出力フレーム数は `floor((t_last − t0) * out_fps) + 1`。
- 各出力時刻 `t0 + k / out_fps` に対し、時刻がそれ以下で最新の入力フレームを返す。
- 画像はコピーせず参照を返す（ジェネレータ）。複製によるメモリ増加はない。
- 入力が1フレームなら、そのフレームを1回だけ返す。
- 時刻が逆行しているフレーム（前のフレーム以下の時刻）は無視する。この分は `n_dropped` に数える。
- 出力フレーム数の上限は呼び出し側のクリップ窓（`max_duration` + 前後マージン）で決まる。現設定（10秒+3秒×2、20fps）で最大約320フレーム。
- 統計は `stats` リストに1件追加する形で返す（ジェネレータの消費完了後に確定する）。

#### 想定される挙動: 再接続直後のバースト

RTSP再接続時、OpenCVが内部にバッファしていたフレームを一括で吐き出すと、それらは全て「受信した瞬間の時刻」を持つ。
本方式ではこれらが1〜2個の出力スロットに集約され、大半が `n_dropped` に数えられる。
再生時間は実時間どおりになるが、バースト分の映像内容は失われる。

これは本方式の想定内の挙動である（受信時刻が撮影時刻を表していない入力に対して、時刻どおりに並べた結果）。
将来この現象を新たな不具合として再調査しないよう、ここに記録する。
根本的に解消するには7章のPTS方式が必要になる。

### 4.3 `save_meteor_event()` と書き出し関数

- `clip_fps = estimate_fps_from_frames(...)` を削除し、`out_fps = sanitize_fps(fps, default=30.0)` を使う。
- `write_mp4_clip_ffmpeg()` と `write_clip_with_fallback()` のフレーム書き込みループを、`resample_frames_to_cfr(frames, out_fps)` の出力を書く形に変える。ffmpegのコマンドライン引数は変更しない。
- 合成画像（composite）の生成は入力フレームをそのまま使う。変更しない。

### 4.4 削除するもの

- `estimate_fps_from_frames()` と `max_ratio_to_fallback` によるクランプ。呼び出し元は `save_meteor_event()` の1箇所のみ（grepで確認）。
- `sanitize_fps()` は `RTSPReader` と書き出し関数が使うため残す。

### 4.5 変更しないもの

- 検出ロジック（`track_objects`、速度・`duration` の計算）。本リリースでは変更しない。

  ただし**未検証の懸念として残す**。2.1で確認したのはクリップ全体（約6.6秒）での受信時刻と実時間の一致であり、検出イベント（0.2〜0.6秒）という短い窓の中で受信時刻が局所的に圧縮されていないことは確認していない。速度（px/s）と `duration` はこの短い窓の受信時刻から計算されるため、局所的に2倍圧縮されていれば速度も2倍に出る。

  これはcamera2/camera3で運用中の `TWILIGHT_MAX_SPEED=700`（薄明期の速度上限、鳥の除外用）に影響しうる。速度が過大に出た本物の流星が薄明期に除外されている可能性がある。

  検証方法: 数件の検出について、OSD時刻から実時間ベースの速度を再計算し、JSONLに記録された `length_pixels` / `duration` 由来の速度と比較する。本設計の範囲外とし、別途実施する。
- `RTSPReader` の時刻の付け方（7章の結果次第で変更の可能性あり）。
- `meteor_detector_common.py`、`astro_utils.py`。

## 5. 影響範囲

- 全カメラの検出クリップ書き出しに影響する。検出の可否、検出件数、JSONLの記録内容には影響しない。
- 夜間クリップのフレーム数は現在の約2倍になる（実効10fps、出力20fpsの場合）。複製フレームは直前との差分がほぼゼロで、x264ではファイルサイズの増加は小さい見込み。増加量は実機で計測する（6.2）。
- ダッシュボード、API、設定項目に変更はない。
- 過去に書き出し済みのクリップは修正されない。必要な場合は `memory/log_server-changes.md` 2026-08-24の手順（OSD実測+無劣化の再ラップ）で個別に対応する。

## 6. 検証

### 6.1 ユニットテスト（コンテナ内 `pytest -q`）

| ケース | 期待 |
|---|---|
| 等間隔10fpsの入力、`out_fps=20` | 各フレームが2回ずつ出力され、出力フレーム数/20が入力の時間幅と一致 |
| 等間隔20fpsの入力、`out_fps=20` | 入力と同じ列 |
| 間隔が0.05秒、0.05秒、0.2秒の繰り返し（現行の中央値推定が20fpsを返す入力） | 時間幅が一致し、かつ入力フレームの脱落が0件 |
| ほぼ同時刻のフレームが半数を超える入力（現行が200fps前後を返す入力） | 時間幅が一致し、脱落件数が入力の同時到着数と一致する |
| 途中で10fpsから20fpsに変わる入力 | 時間幅が一致し、複製連長が区間ごとに2→1へ変わる |
| 途中に2秒の欠落がある入力 | 欠落区間は直前フレームの複製で埋まる |
| 1フレームのみ、時刻の逆行、空リスト | 例外を出さない |
| `write_mp4_clip_ffmpeg()` のffmpeg引数 | `-r` が `out_fps` になっている |

#### 再配置品質の指標

`duration` が実時間と一致することは、本方式では構成上そうなるだけで検証にならない。
本方式が新たに持ち込むリスクは、再生時間が正しいまま動きがカクつくこと（受信時刻が偏ると、複製が偏り、一部の入力フレームが出力に現れない）である。

`resample_frames_to_cfr()` は再配置の統計を返す。

| 項目 | 意味 |
|---|---|
| `n_out` | 出力フレーム数 |
| `n_used` | 出力に現れた入力フレーム数 |
| `n_dropped` | 出力に一度も現れなかった入力フレーム数 |
| `max_run` | 同一フレームの最大連続回数 |

**`n_dropped=0` は正常時の期待値にならない。**
受信間隔には常にジッタがあり、格子間隔（0.05秒）より短い間隔で届いたフレームは同じスロットを奪い合って一方が脱落する。
2026-09-17にgreeng4のcamera1で実測した受信間隔（公称0.05秒に対し0.031〜0.066秒）を再配置にかけると、正常時でも以下の脱落が生じる。

| 条件 | 脱落率 | `max_run` |
|---|---|---|
| 昼間（実効20fps、格子20fps） | 7〜11% | 2 |
| 夜間（実効10fps、格子20fps） | 1.5% | 3 |
| 同時到着バースト（異常） | 33% | 1 |

したがって判定は脱落率で行う。閾値は正常時の上限（11%）と異常時（33%）を分離する `RESAMPLE_DROP_WARN_RATIO = 0.25` とし、これを超えた場合のみ警告をログに出力する。

`max_run` は動きのカクつきを直接示す指標である。格子間隔より短い間隔で届いたフレームが脱落しても見た目には影響しないが、多数のフレームが1スロットに集中し、その後に空白が続く（クランプ）とカクつく。

### 6.2 実機検証（greeng4、デプロイ後の最初の夜）

- 夜間の検出クリップについて、`[WARN] クリップ再配置` のログが出ていないことを確認する。出ている場合は受信時刻の偏りがあり、7章のPTS方式への切り替えを検討する。
- 夜間クリップ1件以上でOSD時刻の経過秒とMP4の `duration` を比較する（構成上一致するはずだが、実装の誤りを検出するためのスモークチェック）。
- 昼間の検出クリップ1件以上で同じ確認をする。
- クリップのファイルサイズを確認する。デプロイ前の計測（2560x1440、Mac上のコンテナ、preset medium）では、夜間クリップが6.1MB/64フレームから12.5MB/127フレームへ約2倍になった。複製フレームは差分がほぼゼロだがx264のCFR出力では実フレームとして符号化されるため、サイズは出力フレーム数に比例する。
- 書き出し所要時間を確認する。同計測では3.6秒から6.5秒へ増えた（Mac上の値。N100はより遅い）。

  書き出しは検出ループ内で同期実行される（`meteor_detector_rtsp_web.py:316` 他）。その間 `reader.read()` が呼ばれないため、受信スレッドのキュー（上限30枚）にフレームが溜まる。夜間10fpsなら30枚は3秒分であり、書き出しが6.5秒かかるとキューが溢れ、その区間のフレームが失われる。

  ただしフレームの受信時刻は `cap.read()` の時点で付与される（`meteor_detector_realtime.py` の `_read_loop`）ため、キューに滞留しても時刻は正しい。したがって書き出し遅延は「欠落」を生むが「時刻の圧縮」は生まない。新方式は欠落区間を直前フレームの複製で埋めるため、再生時間は実時間を保つ。
- 検出件数を確認する。ただし**前夜との単純比較はできない**。天候・月齢で日ごとの変動が大きいためである（下表）。

  | 日付 | camera1 | camera2 | camera3 |
  |---|---|---|---|
  | 2026-09-10 | 1 | 12 | 16 |
  | 2026-09-11 | 59 | 5 | 12 |
  | 2026-09-12 | 1 | 2 | 41 |
  | 2026-09-13 | 0 | 6 | 32 |
  | 2026-09-14 | 4 | 9 | 126 |
  | 2026-09-15 | 96 | 10 | 93 |
  | 2026-09-16 | 5 | 0 | 13 |
  | 2026-09-17 | 1 | 0 | 5 |

  判定は「camera3が0件」のような明らかな停止の有無に限る。件数の増減は本変更の評価材料にしない。

  **別件として要調査**: camera2は9/16・9/17が0件である。本変更より前からの事象であり、本設計の範囲外。

## 7. 夜間の受信時刻のばらつきについて

**（2026-09-17 19:12に計測し解決。7.1・7.2を参照）**

当初の懸念は以下のとおりだった。

本設計は、受信時刻が撮影時刻におおむね比例することを前提にしている。
クリップ全体の長さでは確認できた（2.1）が、夜間のフレーム単位のばらつきは分かっていない。
ばらつきが大きい場合、再生時間は正しくても、複製と間引きが不規則に入って動きがカクつく。

昼間（2026-09-17 17:50頃、camera1コンテナ内で15秒間）の実測では、受信間隔は公称0.05秒に対し0.031〜0.066秒に分布していた。
このばらつき自体は本方式で吸収できる範囲であり（6.1の脱落率の表を参照）、本設計のまま実装した。

当初、camera1コンテナ内で `cv2.VideoCapture` を開いて40秒間計測する予定だったが**中止した**。
これは稼働中の検出プロセスとは別に、同じカメラへ2本目のRTSPセッションを張ることになる。
Tapo C120は同時接続数に制限があり、2026-08-25にはcamera1でセッション断（`Stream timeout triggered after 30xxx ms`）が頻発した記録がある。
新コードの初日に、計測自体が検出を妨害し、かつ競合で歪んだ値を測ることになるため取りやめた。

代わりに以下で確認する。いずれも接続を増やさない。

1. 稼働中の検出プロセスが公開する `/stats` の `runtime_fps` を読む（`meteor_detector_rtsp_web.py:224` が直近30フレームの受信時刻から算出している）。デプロイ直後18:26の値は camera1=14.58、camera2=14.98、camera3=19.34（いずれも `source_fps=20.0`）。完全に暗くなった後に再度読み、夜間の実効fpsを確認する。
2. 実際のクリップに記録される再配置統計（`max_run` と脱落率）を見る。これは本番の負荷・本番のタイムスタンプで計測された値であり、別途の計測より確実である。

### 7.1 計測結果（2026-09-17 19:12、日没後）

`/stats` の `runtime_fps` を3秒間隔で5回サンプリングした（camera1）。

| 項目 | 値 |
|---|---|
| 実効fps（5サンプル） | 10.01 / 10.05 / 10.02 / 10.04 / 10.01（平均10.03） |
| 3カメラの実効fps（19:12） | camera1=10.06、camera2=10.00、camera3=9.54 |
| ネゴシエーション値 | 20.0（昼夜とも変わらず） |

夜間の実効fpsは10fps前後で安定しており、サンプル間のばらつきは0.04fps以内だった。

この実効fpsに人工的なジッタを加えて再配置にかけた結果は以下のとおり。

| 受信間隔のジッタ | 再生時間の差 | 脱落率 | `max_run` |
|---|---|---|---|
| ±0% | 0.019秒 | 0.8% | 2 |
| ±15% | 0.012秒 | 0.8% | 3 |
| ±30% | 0.004秒 | 0.8% | 3 |

ジッタが±30%あっても、脱落率は警告閾値（25%）を大きく下回り、`max_run` も3に収まる。

### 7.2 判断

**本設計のまま運用する。** PTS方式への変更は行わない。

夜間の実効fpsが安定しており、想定される範囲のジッタでは再生時間・脱落率・`max_run` のいずれも問題ない。
ただし本節の検証は人工的なジッタによるものであり、実際の受信間隔の分布そのものは測っていない。
実データによる確認は、6.2の実クリップの再配置統計で行う。

この計測は、2.3の仮説（受信間隔の偏りで中央値が狂う）の検証も兼ねる。

なお本方式の正しさはこの計測結果に依存しない。
受信時刻が偏っていても再生時間は実時間を保つ（偏りは `max_run` と脱落率として観測される）。
計測は、カクつきの有無を確認し、PTS方式へ進むかを判断するためのものである。

## 8. リリース

- 種別はバグ修正。バージョンはPATCHを上げる（v3.17.5）。
- 変更禁止ファイルを含むため、挙動変更の規模にかかわらずreviewerのレビューを通す。
- コミット時、検出コア保護のpre-commitフックには正規のバイパス変数 `METEOR_CORE_OK=1` を使う（`--no-verify` は使わない）。
- greeng4へのデプロイはGit経由（`git pull` → `./meteor-docker.sh rebuild`）。実施時刻は検出開始前とし、ユーザー承認後に行う。
