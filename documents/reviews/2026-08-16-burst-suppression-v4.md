## 合格項目

- **指摘1（承認ブロック）の是正は構造的に正しい。** `add_event()` は `_is_mergeable(self.pending[-1], event)` が真の場合のみマージを行い、到着ログへの加算をスキップする。以下の点を実際にコードを実行して確認した。
  - `_merge()` は `start_time=prev.start_time` を保持するため、マージ後イベントの `start_time` は最初の断片のものと一致し続ける。したがって到着ログに積まれた1件の値と、最終的に確定するマージ済みイベントの `start_time` は常に一致し、`_reject_bursts()` の集合照合（`e.start_time not in burst_times`）に不整合は生じない。
  - `_prune_arrival_times(event.start_time)` はマージ時も生の新断片の `start_time`（`prev`ではなく`new`側）を渡すが、内部で `horizon = min(oldest_pending, current_time)` として `pending[0].start_time` を基準に取るため、渡された引数の違いは枝刈り基準を安全側（より古い方）に倒すだけで、誤って必要な記録を消す方向には効かない。
  - 修正前コードに戻すと新規テスト（`test_event_merger_does_not_burst_reject_merged_fragments`）が失敗することを本レビューでも再現した。
- **6断片の再現テストを実際に実行し、断片が「1件」ではなく「2件」にマージされることを確認したが、これは今回の修正の妥当性を損なわない。** `_is_mergeable(prev, new)` はマージ後に更新された `pending[-1]`（累積結合済みイベント全体）と次の生断片を比較するため、断片同士を単独ペアで見れば全てマージ条件を満たしていても、`speed_ratio` が累積の `length/duration` から再計算されることで、あるタイミングでマージ条件を割り込み新規到着として扱われうる（本件では4番目の断片で発生）。これは `_merge()` の既存の意味論（結合後は結合済み全体の速度で以降の断片と比較する）であり、指摘1の修正範囲外の既存挙動。2件になった場合でも両方とも正しく保存され、破棄されないことを確認した。
- `pytest tests/test_meteor_detector_realtime.py` 20件全通過、`flake8` クリーンを本レビューで再現確認した。
- `documents/DETECTOR_COMPONENTS.md` に「マージ経路との相互作用（重要）」の節が新設され、指摘1の内容（原因・実測事例・修正方針）が正確に記載されている。
- `CHANGELOG.md` の `SHUTDOWN_SAVE_BUDGET_SEC` に関する記述は「解消ではなく緩和」である旨を明記しており、v2指摘4／v3指摘4は本レビューで解消と判定する。
- `_run_merger`（テストヘルパー）は本番と同じ `add_event()` → 内部 `flush_expired()` の経路を通しており、`pending.extend()` + `flush_all()` 1回のショートカットで最良ケースのみを検証する設計にはなっていないことを確認した（過去レビューで繰り返し指摘してきた経路不一致の再発なし）。

## 指摘事項

### [重大度: 中] tests/test_meteor_detector_realtime.py:232-247（`test_event_merger_handles_non_monotonic_arrival_order`） — アサーションが結果の中身を検証しておらず、実際には全件破棄という重要な挙動を見落としたまま緑になっている

このテストの最終アサーションは以下のみである。

```python
finalized = _run_merger(merger, events, advance_to=200.0)
assert isinstance(finalized, list)
```

`_run_merger()` は常にリストを返す実装であるため、このアサーションは常に真になる（何を入力しても失敗しえない）。実際にこのテストのデータで何が起きているかを本レビューで実行して確認した。

```
arrivals = [100.00, 100.05, 100.10, 99.90, 100.15, 100.20, 100.02]
sorted:  [99.9, 100.0, 100.02, 100.05, 100.1, 100.15, 100.2]
gaps:    [0.1, 0.02, 0.03, 0.05, 0.05, 0.05]   （全て burst_window_time=1.0 以内）
burst_max_events = 5
結果: finalized == []（7件全て破棄、[WARN] 同時刻バーストを検出: 7件のイベントを破棄）
```

座標を大きく離してマージが起きないようにしているため、7件全てが単一クラスタとして扱われ、`burst_max_events`（5）を超えるためバーストと判定され全件破棄される。これは意図した挙動である可能性が高い（座標が離れており本来無関係な7件なので、密な到着間隔だけでバースト判定するのは方式の定義通り）が、**テストのdocstringは「非単調な到着で不正な状態にならないこと」を目的として書かれており、「全件破棄されるのが正しい」ことは検証していない**。

前回（v3）指摘3で要求したのは「`sorted()`ベースのクラスタリングが正しく機能し、限界件数超過時は全件、非超過時は全件保持されることを検証する」ことだったが、本テストは超過時に全件破棄されることを主張も検証もしていない。将来このロジックが壊れて「非単調到着時は誤って例外を投げず単に何も破棄しない」というような回帰が起きても、このテストは検出できない（`isinstance(x, list)` は空リストでも非空リストでも真）。

**要求する是正の方向性（実装は行わない）:** `assert finalized == []` （または期待する具体的な中身）に置き換え、非単調到着でも「クラスタリングの結果自体が正しい」ことを保証するテストにすること。
