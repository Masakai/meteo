## 合格項目

- **`estimate_fps_from_frames()` の是正は妥当**（上表のとおり）。テスト5件は本番実測値を再現しており、リグレッションガードとして機能する。
- **`_reject_bursts()` のアルゴリズム自体（単一バッチ内での判定）は正しい。** スライディング窓の実装（`head` の単調前進、`tail - head + 1 > limit` の判定）にオフバイワンはなく、`window <= 0` / `limit <= 0` のガードも入っている。**問題は窓のロジックではなく、窓を適用する範囲（スコープ）にある**（指摘1）。
- **`id()` ベースの同一性判定は現状安全**（観点2への回答）。`_reject_bursts()` の実行中は `ordered` と `events` の両リストが全オブジェクトへの参照を保持するため、GCによるidの再利用は起こらない。同一 `MeteorEvent` が複数回現れる可能性も、`flush_expired()` は `popleft()` で `pending` から取り除きながら1回だけ `finalized` に積み、`flush_all()` は `list(self.pending)` を1回だけ作るため、両経路とも重複はない。`add_event()` の `self.pending[-1] = self._merge(...)` も新しいオブジェクトを差し替えるだけで重複を生まない。指摘としては低（可読性のみ、指摘7）。
- **`flush_expired` / `flush_all` の両経路に適用漏れはない**（観点2への回答）。`_reject_bursts` の呼び出し箇所を全 grep で確認し、`EventMerger` から確定イベントが外部に出る経路はこの2メソッドのみ（`add_event()` は内部で `flush_expired()` を呼ぶだけで、独自の出口を持たない）であることを確認した。

## 指摘事項

### [重大度: 高] meteor_detector_realtime.py:777-812 — `_reject_bursts()` の判定が「1回のflush呼び出しで返る分」に限定されており、実運用の主要経路でバースト抑制が最大100%機能しない

**これが本レビューで承認をブロックする中心的な欠陥である。**

`_reject_bursts()` は引数 `events`（＝そのflush呼び出しが返す分だけ）の中でしか集中を判定しない。一方、実運用では `flush_expired()` はフレームごとに呼ばれ（`meteor_detector_rtsp_web.py:336`）、`end_time < timestamp - merge_max_gap_time` を満たしたイベントだけを少数ずつ排出する。したがって、**同一バーストのイベント群が複数回のflushに分割して排出されると、各バッチは「少数のイベント」にしか見えず、バーストとして認識されない。**

脱出経路は2つある。

1. `len(events) <= limit` の早期リターン（789行）: 1回のflushが5件以下を返す限り、判定は一切行われない。
2. スライディング窓がバッチ内に閉じている: バッチをまたいだ集中は原理的に見えない。

**実測（`add_event()` → 毎フレーム `flush_expired()` という本番と同じ経路で158件バーストを再現）:**

| 各イベントの `end_time` のばらつき | 保存されてしまう件数 |
|---|---|
| 0.00秒（全track が同一フレームで終了） | 2 / 158 |
| 0.01秒刻み（全体で約1.6秒に分散） | **38 / 158** |
| 0.05秒刻み（20fpsで1フレームずつずれる） | **158 / 158（抑制がまったく効かない）** |
| 0.10秒刻み | **158 / 158** |

再現コード（`_event()` は既存テストのヘルパー相当）:

```python
params = DetectionParams()
m = EventMerger(params)
for i in range(158):
    st = 5328.271 + (i % 3) * 0.096          # start_time は0.192秒幅に集中（実データどおり）
    m.add_event(_event(st, st + 0.40 + i * 0.05, ...))   # end_time だけ1フレームずつずれる
total = 0
t = 5328.3
for _ in range(600):                          # 20fpsの検出ループを模擬
    t += 0.05
    total += len(m.flush_expired(t))
total += len(m.flush_all())
# => total == 158（1件も破棄されない）
```

**`end_time` のばらつきは例外ではなく通常の姿である。** `_finalize_track()`（684-685行）は `start_time=min(times)`, `end_time=max(times)` を各トラックから独立に算出する。バーストでは多数のトラックが別々の座標で独立に生起・消滅するため、終了フレームが揃う理由がない。加えて `DetectionParams.min_duration=0.1` / `max_duration=10.0`（300-301行）は `end_time` の分散を100倍まで許容している。したがって上表の「0.05秒刻み」「0.10秒刻み」は病的な仮定ではなく、**むしろ既定の想定ケース**である。

さらに悪いことに、この失敗はトリガー条件と相関する。1回のflushが返す件数は、フレーム到着間隔とループ周回速度に依存する。CPU飽和時にはループが遅くなり排出パターンが変わるが、**CPU飽和こそがバーストの引き金かつ本対策が守ろうとしている状況そのもの**である。守るべき局面で保証が崩れる設計は保証とは呼べない。

なお、依頼文にある実データ（`start_time` が0.192秒幅・ユニーク値3個）は `start_time` の分布であって `end_time` の分布ではない。本レビュー時点で `detections.db` はローカルでは空（テーブル0件）であり、当該158件の `end_time` 分布は確認できなかった。**ただし確認結果がどうであれ、この指摘の重大度は下がらない。** 仮に当該バーストの `end_time` が偶然揃っていて現行コードで捕捉できたとしても、それは1事例がたまたま最良ケースに当たったにすぎず、上表が示すとおり分散がわずか0.05秒/件に増えるだけで抑制率は100%から0%に落ちる。

**要求する是正の方向性（実装は行わない）:** 判定の状態をflush呼び出しをまたいで保持する必要がある。すなわち `EventMerger` 自身が確定済みイベントの時刻履歴（またはバースト判定済みの時間区間）をインスタンス変数として保持し、`_reject_bursts()` は「今回のバッチ ∪ 直近の履歴」に対して窓判定を行う設計に変える。あわせて、いったんバースト区間と判定した時間帯に後から到着したイベントも破棄する（区間ベースの抑制）ことで、分割排出に対して安定する。

### [重大度: 高] tests/test_meteor_detector_realtime.py:96-148 — バーストテスト4件が本番の呼び出し経路を一切通っておらず、上記の欠陥を検出できない

追加された4件（`test_event_merger_rejects_simultaneous_burst` / `..._keeps_normal_meteor_events` / `..._keeps_burst_at_threshold` / `..._rejects_only_burst_window`）は、いずれも

```python
merger.pending.extend(events)

```

という形で、**内部状態 `pending` を直接操作し、全イベントを1バッチで `flush_all()` に流している**。これは `_reject_bursts()` が唯一正しく機能するバッチ構成であり、実運用の経路（`add_event()` → 毎フレーム `flush_expired()`）を一度も実行していない。テストが緑なのは、テストが欠陥の存在しない条件だけを選んで再現しているためである。

これは前回指摘1と**同じ欠陥クラスの再発**である。前回は「既存の120上限に吸収されて新ロジックに到達しないテスト」、今回は「欠陥の起きないバッチ構成しか作らないテスト」であり、いずれも*ガードすると称する挙動に到達していない*点で共通する。前回のレビューでプロジェクトメモリに記録した検証規律（`.claude/agent-memory/reviewer/project_fps_estimation_clamp.md`）が、fps側には適用されたがバースト側には適用されなかった形である。

### [重大度: 中] meteor_detector.py:955 / meteor_detector_rtsp.py:114 — 依頼のスコープ外の2経路にも挙動変更が波及している

`EventMerger` は本変更でスコープとして挙げられた `meteor_detector_rtsp_web.py` 以外に、`meteor_detector.py:955`（動画ファイル解析）と `meteor_detector_rtsp.py:114`（RTSP CLI版）でも生成されている（grep で全生成箇所を確認済み）。`_reject_bursts()` は `EventMerger` 側に実装されたため、**この2経路でも検出結果が無言で破棄されるようになる。**

### [重大度: 中] meteor_detector_rtsp_web.py:311-339 — 対策Bの停止時挙動（観点3への回答）

**結論として、データ損失のトレードオフは実質的に発生しない。追加のバッファ退避は不要である。**

根拠: 検出ループ脱出後の終了処理（`meteor_detector_rtsp_web.py:396-410`）は `detector.finalize_all()` → `merger.add_event()` → **`merger.flush_all()`** を実行しており、ここには `stop_flag` チェックが入っていない。したがって、新しい `break` で保存をスキップされたイベントのうち `pending` に残っているものは、終了処理の `flush_all()` 経路で拾われて保存される。

ただし2点の副作用を確認すること。

1. **`break` の時点でローカル変数に取り出し済みのイベントは、どの終了処理経路でも回収されず完全に失われる。** 該当するのは2種類ある。
   - `merged_events` / `expired_events` として既に `pending` から取り出された分。`pending` にはもう存在しないため `flush_all()` では拾われない。
   - **外側の `for event in events:` の `break`（311行）で処理されずに残った分。** `events` は `detector.track_objects()` の戻り値であり、その生成元 `_finalize_track()` は `self.active_tracks.pop(track_id)`（609行）でトラックを取り除いている。すなわちこれらのイベントは `pending` にも `active_tracks` にも存在せず、終了処理の `detector.finalize_all()` でも `merger.flush_all()` でも回収できない。

   いずれもバースト由来であれば望ましい挙動だが、正常なシャットダウンで正常な流星が1〜数件失われうる点は仕様として認識すべきである。損失は「停止要求が来た1周分」に限定されるため、バッファ退避などの追加機構は不要と判断する。
2. **終了処理の `flush_all()` 側には `stop_flag` チェックがないため、対策Bが解決しようとした「join(5秒)がタイムアウトする」問題はこの経路では解消していない。** `pending` に多数のイベントが残った状態で停止すると、終了処理側で大量のMP4書き出しが直列に走り、やはりjoinがタイムアウトする。指摘1の欠陥と組み合わさると、バースト時にまさにこの状態になりうる。対策Bの効果を完結させるには終了処理側にも上限または中断条件が要る。

`state.detection_count` との整合は問題ない（合格項目に記載のとおり `break` はインクリメントの前にある）。

### [重大度: 中] fpsクランプの限界について（観点4への回答）— 提案されている代替式は機能しない

**提案された `fps = (n-1) / (frames[-1][0] - frames[0][0])` は、現行の `1/median_dt` と数学的にほぼ同値であり、問題を解決しない。**

実測（依頼文のフレーム数を用いて算出）:

| クリップ | フレーム数 | 受信時刻の全幅 | `(n-1)/span` | 現行（中央値ベース） |
|---|---|---|---|---|
| East `79d9e49b` | 65 | 0.593秒 | **108.00fps** | 108fps →（クランプ後）20.0 |
| South `7f6b0f81` | 96 | 0.812秒 | **117.00fps** | 117fps →（クランプ後）20.0 |

両式とも**同じ受信時刻**から導出されるため、受信時刻そのものが圧縮されている本故障モードでは同じ誤った値を返す。OSD実測では East は6秒・South は17秒の実経過があったのに対し、受信時刻の全幅は0.593秒・0.812秒しかない。つまり `cap.read()` がバッファ済みフレームを連続して吐き出しており、**撮影間隔の情報は受信時刻から失われている**。式を変えても復元できない。

**したがって、真の実効fpsは受信時刻からは原理的に復元不可能である。** 取りうる立場は次のとおり。

- **推奨: 現行のクランプを「緩和策」と位置づけ、残存する倍速再生（East 約1.9倍・South 約3.6倍）を既知の限界としてCHANGELOGとドキュメントに明記する。** 式の変更は推奨しない（効果がないため）。
- 真値を得るには受信時刻以外の情報源が要る。候補は (a) カメラのRTPタイムスタンプ（`cap.read()` の受信時刻ではなくストリーム内のPTSを使う）、(b) ネゴシエーション値 `fallback_fps` を常に採用する（実効fpsの正常な低下は捨てる）、(c) OSDのOCR（非現実的）。いずれもスコープが大きく、本リリースに含めるべきではない。
- **本質的な解決は上流にある。** 対策Aがffmpegの大量起動を止めればCPU飽和が緩和され、受信時刻の圧縮そのものが起きにくくなる。この意味で対策Aは対策の本丸であり、だからこそ指摘1の是正が重要である。

この限界を許容してよいかという問いへの回答: **許容してよい。ただし黙って許容するのではなく、既知の限界として文書化すること**（現状のCHANGELOGには倍速再生が残る旨の記載がない）。

### [重大度: 低] 閾値1.0秒/5件の妥当性（観点1への回答）

**現行の閾値を妥当と判断する。** ペルセウス座流星群のピーク時であっても、1台のカメラの画角内で1秒間に6件以上の独立した実流星が写る確率は無視できる（ZHR換算でも1カメラあたりの実測レートは毎分数個の桁）。

実際に警戒すべきは「1個の流星が6個以上のトラックに分裂する」ケースだが、これに対しては本番実データ16,149件・目視ラベル済み「流星」80件（camera1: 23件、camera2: 28件、camera3: 29件）が1件も破棄されないという検証が反証になっている。この検証は8月中旬（ペルセウス座流星群の時期）のデータを含んでおり、懸念される時期をカバーしている。

ただし報告書として次を求める。**この検証の母数（80件）と手法をリリースノートまたはドキュメントに残すこと。** 80件という標本は、閾値の安全性を「実データで確認した」と言える最小限の規模であり、根拠が追跡可能な形で残っていないと、将来閾値を触る人が同じ検証をやり直せない。あわせて指摘4（調整可能化）とセットで扱うこと。

なお、この検証は指摘1の欠陥がない前提（全件が1バッチで判定される）で行われたものである。指摘1を是正すると破棄判定が実際に効くようになるため、**是正後に同じ安全性検証をやり直すこと。**

### [重大度: 低] meteor_detector_realtime.py:806-810 — `id()` ベースのフィルタより添字ベースのほうが明快

前述のとおり現状は安全だが、`id()` の一致でオブジェクトを選別する実装は、将来 `MeteorEvent` の生成経路が変わったとき（例: 同一オブジェクトの再利用やコピー）に静かに壊れうる。`ordered` を作った時点で添字の対応が取れているので、`[ordered[i] for i in range(len(ordered)) if i not in rejected]` で十分であり、元の順序を保ちたいなら `events` の列挙時に添字を持ち回る形にできる。可読性の指摘であり、必須ではない。

### [重大度: 低] `# pragma: no cover` 領域のテスト可能性（観点5への回答）

**今回のスコープでは切り出しを求めない。** 対策Bは `detection_thread_worker()` という巨大関数の内側にあるが、この関数はRTSP接続・OpenCV・スレッドに強く依存しており、切り出しは本変更より大きなリファクタリングになる。CLAUDE.mdの「スコープを守る」原則に照らし、バグ修正のついでに行うべきではない。

一方、**承認をブロックする指摘1・2はいずれも `_reject_bursts()` という既にテスト可能な純粋関数側にある**ため、テスト不能領域の存在は本レビューの判定に影響しない。将来の課題として「保存ループを `_save_events(events, stop_flag, ...)` のような関数へ切り出す」ことを記録するに留めることを推奨する。

### [重大度: 低] 前回指摘4・5・8が未対応

前回「承認ブロックなし」とした指摘のうち、4（クランプ発動時のWARNログ）、5（`fallback_fps` 信頼性への依存の明記）、8（`max_ratio_to_fallback` をキーワード専用に）が未対応のまま残っている。

特に指摘4は、今回OSD実測で「クランプしても倍速再生が残る」と判明したことで**重要度が上がっている**。クランプ発動はCPU飽和の代理指標であり、無言でクランプすると、対策Aの効果（飽和の緩和）が出ているかどうかを検出動画から観測できない。対策Aの効果測定手段として、今回あわせて入れることを推奨する（`_reject_bursts()` 側には既にWARNログがあるので、粒度も揃う）。

## 総評

- 判定: **要修正**

対策Bの孤児スレッド修正は、症状（削除しても次々記録される）から原因（保存ループに停止チェックがない）への切り分けが実ログで裏付けられており、修正内容も適切である。fpsクランプは前回の承認ブロック指摘1・2・3がすべて是正され、特に指摘3への対応でOSD実測という手間のかかる検証を行い、**自らの修正が想定どおりに機能しないことを発見して報告した**点は、レビュー対象として信頼できる進め方である。根本原因の分析（因果が逆だったという発見、実データ16,149件の集計、80件のラベル突き合わせ）も質が高い。

しかし対策Aは、**実運用の主要経路において最大で100%機能しない**。`_reject_bursts()` の判定が1回のflush呼び出しが返す分にスコープされているため、同一バーストが複数回のflushに分割して排出されると、どのバッチも「少数のイベント」にしか見えない。各イベントの `end_time` が1フレーム分（0.05秒）ずつずれるだけで158件中158件が保存されることを、本番と同じ `add_event()` → 毎フレーム `flush_expired()` の経路で実測確認した。`end_time` は各トラックが独立に消滅した時刻であり、揃わないことがむしろ既定である。加えて、この失敗はCPU飽和時のフレーム到着パターンに依存する、すなわち**守るべき局面で保証が崩れる**。

そしてこの欠陥がレビューまで残った理由は、追加されたバーストテスト4件が `pending` を直接操作して `flush_all()` を1回呼ぶ形しか試していないためである。これは前回指摘1（テストが検証対象に到達していない）と同じ欠陥クラスの再発にあたる。
