## 指摘事項

### [重大度: 高] tests/test_meteor_detector_realtime.py:36-53 — 追加テスト2件がいずれも変更前のコードで通過する（新ロジックを一切検証していない）

**検証結果（実施済み）:** `git stash` で `meteor_detector_realtime.py` のみ変更前に戻し、新テスト2件を実行したところ **2 passed**。

```
tests/test_meteor_detector_realtime.py::test_estimate_fps_from_frames_rejects_burst_timestamps PASSED
tests/test_meteor_detector_realtime.py::test_estimate_fps_from_frames_allows_normal_variation_within_ratio PASSED
```

原因は `sanitize_fps()` の既存の上限120.0。`test_..._rejects_burst_timestamps` は1ms間隔（推定約1000fps）を入力しているが、これは**変更前から** `sanitize_fps` が上限120超として弾き、`default`（＝`sanitize_fps(fallback_fps)` ＝20.0）を返していた。したがって `assert fps == 20.0` は新しいクランプではなく既存の120上限を検証しているにすぎない。もう1件（10fpsの維持）も従来どおりの挙動であり、新ロジックを通らない。

今回導入したクランプを守るリグレッションガードが実質ゼロであり、将来 `max_ratio_to_fallback` の条件を削除・改変してもテストは緑のまま通る。CLAUDE.md が reviewer に課す「テストが実際の動作を検証しているか（形式的なテストでないか）」に抵触するため、重大度「高」とする。

**さらに重要な帰結（ドキュメント／原因認識の誤り）:** 変更前コードが1000fpsを既に弾いていたということは、**本番の108fps・117fpsは「1ms間隔のバースト」では説明できない**。これらの値が出力されたということは、フレーム間隔の中央値が約9.3ms・8.5msという、`sanitize_fps` の有効帯（1.0〜120.0fps）**の内側**に収まる値だったことを意味する。docstring に書かれた「フレームが1ms間隔でバースト到着」という説明は、実際には従来から壊れていなかったケースを記述しており、実際の故障モードを誤って説明している（指摘2参照）。

**要求する是正:** 実際に観測された値を再現するテストへ差し替える。すなわち `fallback_fps=20.0` に対し中央値 `1/108`（および `1/117`）秒間隔のフレーム列を与え、クランプにより20.0が返ることを検証する。これらは変更前コードでは108.0/117.0を返すため、初めて新ロジックのガードとして機能する。

### [重大度: 中] meteor_detector_realtime.py:166-174 — docstringが実際の故障モードを誤って説明している

上記のとおり、1ms間隔バーストは変更前から `sanitize_fps` の120上限で処理されていた。実際に修正が必要だったのは「中央値が1.0〜120fpsの有効帯内に収まりつつ、カメラのネゴシエーション値を大きく超える」領域（今回の108/117fps）である。

現在の docstring はこの区別をしておらず、読んだ開発者に「120超のバーストが未処理だった」という誤った理解を与える。CHANGELOG 執筆時にもこの誤認が伝播する。「CPU飽和による `cap.read()` ブロック後のフレーム連続デキュー」という原因記述自体は妥当なので、**結果として現れる推定値が `sanitize_fps` の有効帯内に収まるため従来の上限では検出できなかった**旨を明記すること。

### [重大度: 中] 未検証 — クランプ後の動画の「再生尺」が変わる可能性が検証されていない

本変更の検証は「メタデータのfps値が20.0になること」で止まっており、利用者から見える性質である**再生尺と再生速度が自然になるか**が確認されていない。

書き出される動画の尺は次で決まる。

```
出力尺 = len(frames) / clip_fps
```

`frames` は `ring_buffer.get_range(event.start_time - 1.0, event.end_time + 1.0)`（844行）で取得される。ここで `1/median_dt` は本質的に `len(frames)/時間幅` に相当するため、**推定器はもともと「再生尺がタイムスタンプの時間幅に一致する」値を算出していた**。したがって108→20へのクランプは、タイムスタンプが正しければ再生尺を約5.4倍に引き伸ばすことになる。本修正が正しいのは、**当該ウィンドウのタイムスタンプが圧縮されて（＝実時間を反映せず）いた場合に限られる**。

どちらであるかはフレーム数で判別できるが、当該2ファイルはgreeng4上にあり手元に存在しないため（`find` で未検出）、本レビューでは確定できなかった。

判別基準は次のとおり。

- **フレーム数が約200以上の場合**: カメラは実際にそれだけのフレームを送っており、20fps換算で約10秒分の実映像が2秒幅にタイムスタンプされていたことになる。クランプ後は内容として正しい速度で再生されるが、**修正前より尺が大幅に長い**動画が出力される。この挙動はリリース時に周知が必要。
- **フレーム数が約40〜60の場合**: バックログなしにタイムスタンプのみが圧縮されていたケースで、クランプにより約2〜3秒の自然な動画に復元される。合格項目の記載どおりで問題ない。

なお `RingBuffer`（325-327行）は `max_frames = int(max_seconds * fps)` で上限が決まるため、バッファ長を超えるフレーム蓄積は起こらない。設定値を踏まえた上限の確認とあわせ、**greeng4上の当該2ファイルに対し以下を実行して確認すること**。

```
ffprobe -v error -select_streams v:0 -show_entries stream=nb_frames,duration,avg_frame_rate -of default=nv=1 <file>
```

`nb_frames / 20.0` が流星イベント＋前後1秒マージンとして妥当な尺かどうかを確認する。これを確認せずに「修正は正しく動作する」と結論づけることは、指摘1で検出したテストの空振りと同種のギャップにあたる。

### [重大度: 中] meteor_detector_realtime.py:194-195 — クランプ発動時に一切ログが出ず、根本原因が観測不能になる

クランプが作動しても警告が出ない。本件の根本原因であるgreeng4のCPU飽和（3カメラで84〜94%、Intel N100・4コア）は**未解決のまま**であり、この変更は症状（出力fps）だけを是正する。ログがないと、CPU飽和の悪化や発生頻度の増加を検出動画から察知できなくなる。

これは調査経緯の事実6で指摘されている構図の再現である。AtomCam2運用期（8/10以前）にバーストが観測不能だったのは、30fps固定バグが出力を塗り潰していたためだった。今回のクランプも、無言で出力を塗り潰す点で同じ観測不能状態を作る。

同ファイル内の他の異常系はいずれも出力している（`[WARN] 動画エンコーダの初期化に失敗しました` 861-863行、`接続失敗` 370行、`ストリーム切断を検出` 399行）。ファイル自身の慣例に合わせ、クランプ発動時に推定値と採用値を含む警告を1行出すことを推奨する（例: `[WARN] 実効fps推定値 {estimated:.1f} がネゴシエーション値 {fallback:.1f} の{ratio}倍を超過。{fallback:.1f}を採用`）。

### [重大度: 中] meteor_detector_realtime.py:194 — `fallback_fps` が信頼できない場合にクランプが弱まる／誤ってクランプする（観点2への回答）

閾値は完全に `cv2.CAP_PROP_FPS`（`meteor_detector_realtime.py:383`）由来の値に依存する。実測した2方向の弱点：

- **fallback が実際より高い場合**（`sanitize_fps` の `default=30.0` が発動したケースを含む）: 閾値が45fpsになり、40fps・44fpsの不正な推定値がそのまま通過する（実測確認済み）。`CAP_PROP_FPS` が信頼できないときにこそクランプが緩むという、望ましくない方向の相関がある。
- **fallback が実際より低い場合**: 従来は正しく書き出せていた推定値が不当に引き下げられる。これが本変更で唯一新規に生じうる回帰経路である。

現行の運用値（ネゴシエーション20.0fps、実効10〜20fps）では実害は想定しにくいが、`fallback_fps` の信頼性が閾値の前提であることをdocstringまたはCHANGELOGに明記すべき。あわせて、本番の接続ログ（`接続成功: {w}x{h} @ {fps:.1f}fps`）を grep し、ネゴシエーション値が実レートを下回って報告される事例がないかを確認しておくことを推奨する。

### [重大度: 低] meteor_detector_realtime.py:194 — 閾値1.5倍の妥当性（観点1への回答）

現行の実測値に照らす限り妥当と判断する。ネゴシエーション20.0fpsに対し許容上限は30.0fps、異常値は108〜117fps（5〜6倍）で十分なマージンがある。Tapo C120の夜間IRモードによるfps低下（10〜20fps）は**下方向**の変動であり、上限クランプとは干渉しない。

ただし境界挙動を確認しておくこと。条件が `>` のため、ちょうど1.5倍（fallback=20に対し30.0fps）は**クランプされる**（実測: 30.0 → 20.0、29.9 → 29.9 のまま）。仕様として意図どおりか確認し、テストで固定することを推奨する。

### [重大度: 低] meteor_detector_realtime.py:194 — 低fps側のクランプ欠如（観点3への回答）

現時点では対処不要と判断する。`sanitize_fps` の下限1.0が0.5fps等を既にフォールバックへ回している（実測確認済み）。未カバーなのは「1.0〜十数fps」の帯域（例: 中央値0.5秒→2fpsとなり10倍のスロー再生になる）だが、調査経緯の事実1のとおり8/16の13件は9〜24fpsで低側の異常は観測されていない。

**変更禁止指定のある検出コアに対し、観測されていない事象を根拠に対称クランプを追加するのはスコープ拡大**にあたるため、将来検討事項として記録するに留めることを推奨する。

## セキュリティ検査結果

本変更に該当する問題は検出されなかった。

- **パストラバーサル:** 変更範囲にファイルパス操作は含まれない。`estimate_fps_from_frames()` は浮動小数の計算のみ。
- **XSS:** テンプレート・HTML出力への変更なし。
- **コマンドインジェクション:** 本変更にシェル呼び出しはない。算出された `clip_fps` は `write_mp4_clip_ffmpeg` 経由でffmpegに渡るが、`sanitize_fps` により1.0〜120.0の有限floatであることが保証されており、シェル経由の文字列混入経路はない。むしろ本変更は ffmpeg に渡る値域を**狭める**方向であり、リスクは減少する。
- **認証情報漏洩:** ログ・出力への認証情報混入なし。ただし指摘3でログ追加を推奨した際は、RTSP URL（認証情報を含む）を出力しないよう注意すること。fps値のみをログすること。
