## 指摘事項

### [重大度: 高] meteor_detector_realtime.py:815-829（`_note_arrival`） — バースト終息直後、`burst_window_time` 秒以内に到着した正常イベントが理由なく巻き込まれて破棄される

`_note_arrival()` はバースト帯を記録した後も `_arrival_times`（到着記録のFIFO）をクリアしない。バースト由来の到着記録は `burst_window_time` 秒間ウィンドウに残り続けるため、バースト終息直後にウィンドウ内へ到着した無関係な1件は、残存記録と合算されて再び `len(_arrival_times) > limit` を満たし、その到着自身の時刻までバースト帯が延長されて破棄される。

**再現・実測（本レビューで自作検証）:**

```python
params = DetectionParams()
m = EventMerger(params)
for i in range(10):
    ev = _event(i*0.1, i*0.1+0.4, (100+i*200,200), (160+i*200,260))
    m.add_event(ev)   # burst_max_events(5) を超える10件のバースト、最後の到着は t=0.9

# バースト終息(t=0.9)から delta 秒後、座標を大きく離し merge_max_gap_time を超える
# 単発の完全に独立したイベントを1件だけ投入する
t = 0.9 + delta
ev = _event(t, t+0.3, (2000, 2000), (2060, 2060))
m.add_event(ev)
```

| delta（バースト終息からの経過秒） | 単発イベントの生死 | 記録された `_burst_ranges` |
|---|---|---|
| 0.05 | **破棄される** | `[(0.0, 0.95)]`（帯が延長） |
| 0.30 | **破棄される** | `[(0.0, 1.2)]` |
| 0.60 | **破棄される** | `[(0.0, 1.5)]` |
| 0.90 | 保持される | `[(0.0, 0.9)]`（帯は延長されない） |
| 0.99 | 保持される | `[(0.0, 0.9)]` |
| 1.00 以降 | 保持される | `[(0.0, 0.9)]` |

境界は `delta < burst_window_time`（既定1.0秒）と正確に一致する。座標を大きく離し `merge_max_gap_time`（1.5秒）を超える間隔を取っているため、これは `_is_mergeable()` によるマージではなく `_reject_bursts()` による破棄である（WARNログ `[WARN] 同時刻バーストを検出: N件のイベントを破棄` の件数にこの1件が含まれることでも確認済み）。

**有界性の確認（連鎖してどこまでも伸びるわけではない）:** バースト終息後、0.99秒間隔（マージされない距離・ギャップ）で15件の独立イベントを連続投入したところ、最初の1件は影響を受けず15件全件が保持された。窓自体が `burst_window_time` でスライドするため、「影」の幅は`burst_window_time`一発分に有界であり、無限に延長される設計にはなっていない。この点は指摘1（前回）の是正を覆すほどの欠陥ではないと判断する。

**影響評価:** 実データ検証（16,149件、指摘8是正）では動画ファイルが残存する731件が1件も破棄されていないが、この検証は既に発生した本番データに対する後追い集計であり、「バースト終息直後1秒以内に来た正常な流星」が過去に実在したかどうかは母数の分布に依存する。今後、雷・雲の明滅の直後（1秒以内）にたまたま実際の流星が写った場合は無条件で失われる。バースト自体が「画面全体の輝度急変」という気象条件下で起きる現象であり、直後に本物の流星が写る事象は稀ではあるが、ゼロではない。

**要求する是正の方向性（実装は行わない）:** バースト判定が確定した時点（`len(_arrival_times) > limit` を満たした瞬間）で、それ以降の新規到着は「新しいバーストの開始候補」として扱うべきであり、既存のバースト帯を延長する材料に使うべきではない。例えば、バースト確定後は `_arrival_times` をクリアする、またはバースト帯の `end` をバースト確定時点の最後の到着時刻に固定し、それ以降の到着は改めて独立に `limit` 超過を判定する、といった設計変更が必要。

### [重大度: 中] meteor_detector_realtime.py:815-829（`_note_arrival`） — `start_time` が非単調に到着すると `begin > end` の不正な区間が生成される

`_arrival_times` は到着順（`add_event()` の呼び出し順）のFIFOであり、値としての `start_time` の昇順を保証しない。`begin = self._arrival_times[0]` は「最も古い到着記録」であって「最小の `start_time`」ではないため、後から到着したイベントの `start_time` がそれより小さい値だと `begin > end` の区間が生成される。

**再現（本レビューで自作検証）:**

```python
# 到着順は 0.5, 0.1, 0.9, 0.3, 0.7（非単調）→ 5件のみなのでlimit超過せず記録なし
# 6件目として start_time=0.2 が到着すると limit(5) を超過
# => _burst_ranges に (0.5, 0.2) という begin > end の区間が登録される
```

`_in_burst_range()` は `begin <= start_time <= end` で判定するため、`begin > end` の区間は事実上常に `False` を返す（範囲チェックが機能しない）。実害の方向としては「バーストを検知し損なう」側（安全側の失敗）であり、指摘1のような正常イベントの誤破棄は起きない。ただし、意図せず判定が無効化される区間が発生する設計不備であり、`_prune_burst_ranges` の `r[1] >= keep_after` 比較にも影響しうる（`end` が本来より小さい値になるため早期に破棄される）。

`start_time` の非単調到着が実運用でどの程度起きるかは `meteor_detector_common.py`（変更禁止ファイル）の追跡・確定順序に依存するため本レビューでは頻度を確定できないが、複数トラックが並行して追跡され、持続時間の異なるトラックが `_finalize_track()` で確定する設計上、起こりうる状況である。

**要求する是正の方向性（実装は行わない）:** `begin` は「ウィンドウ内の到着記録の最小値」として `min(self._arrival_times)` から求めるか、そもそも `start_time` の値ベースではなく到着順インデックスベースで管理する設計に改めること。

### [重大度: 中] tests/test_meteor_detector_realtime.py — 指摘1・2で発見した欠陥に対するリグレッションテストが存在しない

現行の `test_event_merger_rejects_only_burst_window` は、バーストから500秒離れた `isolated = _event(500.0, 500.5, ...)` を使っており、`burst_window_time`（1.0秒）以内の際どいケースを検証していない。したがって指摘1（バースト終息直後1秒以内の正常イベントが巻き込まれる）を検出できない。同様に非単調到着（指摘2）を検証するテストもない。

これは前回指摘2・前々回指摘1と同じ欠陥クラス（「欠陥の起きない条件だけを選んで再現するテスト」）であり、プロジェクトメモリ `.claude/agent-memory/reviewer/project_event_merger_batch_scope.md` に記録した検証規律が、分割排出への耐性には適用されたが、境界値・順序異常のケースには適用されなかった形である。

**要求する是正:** 少なくとも以下2件を追加すること。
1. バースト終息直後（`burst_window_time` 未満、例えば0.5秒後）に座標を大きく離した独立イベントを1件投入し、破棄されない（または、破棄する設計にするなら「その旨を意図として明記した上で」テストが期待どおり通る）ことを検証するテスト。**現行実装では失敗するのが正しい。**
2. `start_time` が非単調に到着するケース（例えば `[0.5, 0.1, 0.9, 0.3, 0.7, 0.2]` のような順序）で `_burst_ranges` に `begin > end` の区間が作られないことを検証するテスト。

### [重大度: 中] meteor_detector_rtsp_web.py:415-439 — `SHUTDOWN_SAVE_BUDGET_SEC=4.0` は「解消」ではなく「緩和」であり、そう理解した上で運用すべき

時間予算のチェック（`if idx > 0 and time.time() > shutdown_save_deadline`）は各 `save_meteor_event()` 呼び出しの**前**に置かれている。したがって実際に許容される超過幅は `SHUTDOWN_SAVE_BUDGET_SEC + 直近1件のMP4再エンコード時間` になる。`libx264 -preset medium -crf 18` の再エンコードが数秒かかるケースでは、4.0秒の予算チェックを入れても `join(timeout=5.0)` は依然タイムアウトしうる。

加えて、`idx > 0` の条件により**1件目は無条件で保存される**（時間予算の外）。`merger.flush_all()` 自体の呼び出しコストと `detector.finalize_all()`（この直前の処理）も予算計測の対象外である。

これは前回指摘5に対する「解消」ではなく「緩和」である。真の受け皿は同時に追加された `detection_thread.join()` タイムアウト時のWARNログ（`meteor_detector_rtsp_web.py:759` 付近）であり、これによって「保存が終わっていない可能性がある」ことを運用者がログから把握できるようになった点は前進だが、joinタイムアウト自体の解消ではない。承認をブロックする水準の欠陥ではないが、**指摘1（バースト終端誤破棄がないシナリオでは`flush_all()`の残件数は少なく抑えられるはずなので、実運用での発現頻度は低いと推測される）と組み合わせて評価すべき事項**として中とする。ドキュメント・CHANGELOGに「緩和策であり完全解消ではない」旨を明記することを推奨する。

### [重大度: 低] meteor_detector_realtime.py:161-199（`estimate_fps_from_frames`） — クランプ発動時のログが依然未実装（前回指摘4・9の再掲）

指摘1（バッチスコープでの判定漏れ）・指摘2（テストが本番経路を通っていない）に対する前回の承認ブロックは、設計変更（判定タイミングを到着時に移す）とテストの書き換え（`add_event()` 経路への統一）によって、**元の指摘が指していた欠陥（分割排出時の判定漏れ）自体は解消された。** これは実測・自己検証コードの両方で確認できた。

しかし、その設計変更を精査した結果、**新たに2つの欠陥が見つかった。**

1. バースト終息直後、`burst_window_time` 秒以内に到着した正常なイベントが理由なく巻き込まれて破棄される（重大度: 高）。境界は `delta < burst_window_time` と正確に一致し、有界（無限に延長されるわけではない）ではあるが、本来保存されるべき検出結果が無条件に失われる。
2. `start_time` が非単調に到着すると `_burst_ranges` に `begin > end` の不正な区間が生成される（重大度: 中）。実害の方向はバースト検知漏れ（安全側）だが、設計として意図しない状態である。

いずれも、書き換えられたテスト（`_run_merger()` 経由の6件）では検出できない。指摘4で求めたとおり、境界値（バースト終息直後）と順序異常（非単調到着）を検証するテストが必要である。

**承認をブロックする指摘: 1。** 指摘2・3・4は同時対応が望ましいが単独では承認をブロックしない（指摘3は「緩和策として妥当」、指摘4はログ追加のみ）。指摘1の是正は「バースト帯の延長条件を、既存のバースト由来到着記録では発火させない」設計変更で足りると考えられ、指摘1（前回）で行った設計変更ほど大きな手戻りにはならない見込みである。

- release-managerへの申し送り:
  - 本レビューは**未クローズ**。指摘1の是正と再レビュー（`documents/reviews/2026-08-16-burst-suppression-v3.md` 等）完了までリリースしないこと。
  - 前回・前々回の承認ブロック指摘（バッチスコープの判定漏れ、テストの経路不一致、fpsクランプの限界の未文書化等）はすべて解消されている。今回新たに見つかった指摘1のみが残存する論点であり、対応の見込みは前2回より小さいスコープと想定される。
  - 対策A（バースト抑制）は全検出経路（`meteor_detector.py` の動画解析CLI、`meteor_detector_rtsp.py` のRTSP CLIを含む）に適用される。指摘1の影響もこの3経路すべてに及ぶ。
  - `SHUTDOWN_SAVE_BUDGET_SEC` による終了処理の時間上限は緩和策であり、`join(timeout=5.0)` のタイムアウトを完全には解消しない。本番反映後もjoinタイムアウトWARNログの発生有無を監視すること。
